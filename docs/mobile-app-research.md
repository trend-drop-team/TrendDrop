# TrendDrop 앱 전환 조사

이 문서는 지금 웹으로만 있는 TrendDrop을 모바일 앱으로 만들 수 있는 방법을 정리한다.
앱 개발 경험이 없는 팀원도 읽을 수 있도록 쉽게 쓴다.

## 1. 앱으로 가는 세 가지 길

웹 서비스를 앱으로 만드는 방법은 크게 세 갈래다.

```text
① 다시 개발      화면을 앱용으로 새로 만든다        (React Native, Flutter)
② 웹뷰           지금 웹 화면을 앱 안에 띄운다      (Capacitor, 네이티브 껍데기 + WebView)
③ PWA            앱을 안 만들고 웹을 설치 가능하게  (manifest + service worker)
```

### ① 다시 개발 (React Native, Flutter)

화면을 앱 전용 부품으로 처음부터 다시 그린다. 진짜 앱처럼 부드럽고 OS 기능을 마음껏 쓴다.
대신 작업량이 가장 크고, 웹과 앱 두 벌의 화면 코드를 유지해야 한다.

- **React Native (Expo)**: React로 만든다. `types/api/` 같은 타입과 로직은 재사용되고, 화면만 다시 짠다.
- **Flutter**: 구글이 만든 프레임워크. Dart라는 별도 언어를 쓴다. 두 OS에서 픽셀 단위로 똑같이 나오고 애니메이션이 부드럽지만, 기존 코드를 하나도 재사용하지 못한다.

### ② 웹뷰 (Capacitor 등)

앱 안에 작은 브라우저 화면(WebView)을 두고, 거기에 지금 웹 화면을 그대로 띄운다.
사용자 눈에는 일반 앱이고, App Store와 Play Store 둘 다 올라간다.

- 화면 코드를 거의 다시 짜지 않는다.
- 카메라·푸시 알림 같은 OS 기능은 플러그인으로 붙인다.
- 감촉과 성능은 웹사이트 수준이다. 네이티브만큼 매끄럽지는 않다.
- 웹을 배포하면 앱 심사 없이 바로 반영된다. 자주 바뀌는 화면에 유리하다.

**Capacitor**는 이 방식을 가장 빨리 만들어주는 도구다. Ionic이 만들었고, 빌드된 HTML/JS/CSS를 앱 파일로 포장한다.
토스·배민 같은 국내 대형 앱도 껍데기는 네이티브로 두고 화면 대부분을 웹뷰로 띄우는 구조를 쓴다.

### ③ PWA (Progressive Web App)

앱을 따로 만들지 않는다. 웹사이트에 manifest 파일과 service worker를 붙이면
브라우저가 "홈 화면에 추가"를 띄우고, 추가하면 주소창 없이 전체 화면으로 열린다.

- 코드 변경이 가장 적고, 배포도 웹 배포 그대로다.
- Google Play에는 TWA(Trusted Web Activity) 방식으로 올릴 수 있다.
- **iOS App Store에는 못 올린다.** 애플은 웹을 감싼 것뿐인 앱을 심사에서 거절한다. Safari에서 홈 화면 추가로만 쓴다.

### 한눈에 비교

| 방식 | 기존 코드 재사용 | 앱 감촉 | iOS 스토어 | 작업량 |
|---|---|---|---|---|
| PWA | 전부 | 웹 | 불가 | 아주 적음 |
| 웹뷰 (Capacitor) | 거의 전부 | 웹 | 가능 | 적음 |
| React Native (Expo) | 타입·로직만 | 네이티브 | 가능 | 큼 |
| Flutter | 없음 | 네이티브 | 가능 | 가장 큼 |

### 섞어 쓸 수 있다

①과 ②는 양자택일이 아니다. 껍데기(탭바, 로그인, 푸시)는 네이티브나 RN으로 만들고,
자주 바뀌는 화면(목록, 상세, 이벤트)은 웹뷰로 띄우는 식이 흔하다.
그래서 실제 결정은 "무엇을 고를까"보다 "어디까지 웹뷰로 두고 어디부터 네이티브로 할까"에 가깝다.

## 2. TrendDrop에 적용할 때 알아둘 점

- 프로젝트는 Next.js 16 + React 19다. 아직 PWA 설정(manifest, service worker)은 없다.
- 앱 안에는 정적 파일(HTML/JS/CSS)만 들어간다. Next.js 서버 컴포넌트와 `app/api` 라우트는 앱 안에서 못 돌린다.
  그래서 서버는 지금처럼 따로 배포해 두고, 앱은 그 서버에 접속하는 구조가 된다.
  (배포된 사이트를 통째로 띄우거나, 화면만 정적으로 빌드해 앱에 넣고 데이터는 API로 받거나. 3번에서 고른다.)
- `server/`와 `app/api`가 이미 분리되어 있어서 어느 쪽으로 가든 유리한 편이다.

## 3. 결정: 웹뷰(Capacitor), 원격 URL 방식으로 시작

### 왜 웹뷰인가

- **콘텐츠가 매시간 바뀐다.** 파이프라인이 매시간 키워드를 갱신하고 랭킹 화면도 자주 손본다. 스토어 심사 없이 웹 배포로 즉시 반영되는 구조가 맞다.
- **UI가 목록과 상세다.** 랭킹 보드, 트렌드 상세, 마크다운 문서. 무거운 애니메이션이 없어서 웹뷰 성능 한계에 걸리지 않는다.
- **코드가 한 벌이다.** RN이나 Flutter로 가면 웹과 앱 화면을 따로 유지해야 한다. 화면 하나 고칠 때마다 두 곳을 고치고 두 번 배포하는 비용이 생긴다. 웹뷰는 웹 배포 한 번으로 끝난다.
- **iOS 스토어에 올려야 한다.** PWA는 iOS App Store에 올라가지 않아 탈락이다.
- **서버가 이미 분리돼 있다.** `server/`와 `app/api`가 나뉘어 있어 나중에 정적 빌드로 옮기거나 다른 클라이언트를 붙이기 쉽다.

### 왜 원격 URL 방식인가

Capacitor로 웹뷰 앱을 만드는 길은 두 가지다.

| | 원격 URL | 정적 빌드 |
|---|---|---|
| 동작 | 앱이 켜지면 WebView가 배포된 사이트 주소로 접속 | HTML/JS/CSS를 앱 안에 담아 둠 |
| Next.js 변경 | 없음 | `output: 'export'` 설정, 서버 컴포넌트를 클라이언트 fetch로 변경 |
| 업데이트 | 웹 배포 즉시 | `cap sync` 후 스토어 업데이트 (Capgo 같은 OTA로 우회 가능) |
| 첫 로딩 | 사이트 여는 속도, 오프라인 불가 | 즉시, 오프라인 가능 |

원격 URL은 코드 변경 없이 하루 안에 폰에서 앱이 뜨는 걸 볼 수 있다. 첫 로딩이나 오프라인이 아쉬워지면 그때 정적 빌드로 옮기면 되고, Capacitor 프로젝트는 그대로 쓴다.

### 진행 순서

1. **Capacitor 설치, 배포 주소 연결.** `npx cap init`으로 앱 이름·번들 ID를 정하고, 설정 파일 `server.url`에 배포 주소를 적는다. Next.js는 건드리지 않는다.
2. **앱 프로젝트 생성.** `npx cap add ios`, `npx cap add android`. Xcode / Android Studio에서 열어 아이콘, 스플래시를 넣고 폰에서 띄워 본다.
3. **푸시 알림 붙이기.** 애플 심사 가이드라인 4.2(최소 기능)는 "웹사이트를 감싸기만 한 앱"을 거절하므로 네이티브 기능이 하나는 있어야 한다. "새 트렌드가 떴을 때 알림"은 TrendDrop에 실제로 의미 있는 기능이기도 하다.
4. **스토어 제출.** App Store, Play Store.
5. **필요 시 정적 빌드로 전환.** 첫 로딩이 느리거나 오프라인이 필요해지면.


### 웹뷰의 단점과 대응

| 단점 | TrendDrop에서 | 대응 |
|---|---|---|
| 감촉이 웹이다 (스크롤, 전환, 뒤로가기) | 가장 체감될 부분 | 뒤로가기 제스처 등은 직접 처리. 심해지면 아래 "다음 단계" |
| 성능 한계 | 목록·텍스트 위주라 문제 없음 | — |
| 첫 로딩, 오프라인 불가 | 원격 URL의 대가 | 정적 빌드로 전환 |
| 애플 심사 거절 위험 | 첫 제출에서 흔함 | 푸시 알림 등 네이티브 기능 하나 이상 |
| 플러그인에 없는 기능은 네이티브 코드 | 당장은 해당 없음 | 필요할 때 Swift/Kotlin |

### 다음 단계: 감촉이 문제가 되면

사용자가 늘고 "앱 같지 않다"가 지적되면 껍데기를 React Native(또는 Flutter) 중 하나로 바꾼다.
그 안에 웹뷰를 띄워 기존 화면은 그대로 두고, 아쉬운 화면만 하나씩 네이티브로 옮긴다.
웹 화면 코드는 계속 살아 있고 껍데기만 갈아끼우는 구조라, 지금의 결정이 나중 선택을 막지 않는다.

## 4. 시작부터 스토어 배포까지

아래 0~3단계는 Capacitor 기준이다. **4~7단계(스토어 준비, 제출, 심사, 운영)와 비용은 Flutter나 React Native로 만들어도 똑같다.** 앱을 어떤 기술로 만들든 스토어에 올리는 절차는 하나다.

### 0단계. 준비물

- Mac + Xcode (App Store에서 설치). iOS 빌드는 Mac에서만 된다.
- Android Studio.
- Apple Developer Program 가입. 승인까지 하루 정도.
- Google Play Console 가입.
- 웹이 HTTPS 주소로 배포되어 있어야 한다. WebView는 HTTP를 기본으로 막는다.

### 비용

| 스토어 | 비용 | 비고 |
|---|---|---|
| Apple App Store | 연 99달러 | 매년 갱신. 갱신 안 하면 앱이 내려간다 |
| Google Play | 1회 25달러 | 이후 비용 없음 |

둘 다 개발자 계정 비용이다. 앱이 무료면 그 외에 스토어에 내는 돈은 없다. 유료 앱이나 인앱 결제를 하면 매출의 15~30%를 수수료로 떼지만 TrendDrop은 해당 없다.
개인 명의로 가입해도 되고, 법인 명의면 서류가 더 필요하다.

### 1단계. Capacitor 붙이기 (반나절)

```bash
npm install @capacitor/core @capacitor/cli
npx cap init          # 앱 이름, 번들 ID(예: com.trenddrop.app) 입력
```

생성된 `capacitor.config.ts`에 배포 주소를 적는다.

```ts
server: { url: 'https://trenddrop.example.com' }
```

앱 프로젝트를 만든다. `ios/`, `android/` 폴더가 생긴다. Next.js 코드는 건드리지 않는다.

```bash
npx cap add ios
npx cap add android
```

### 2단계. 폰에서 띄워보기 (반나절)

- `npx cap open ios` → Xcode가 열림 → 아이폰 연결 → 실행.
- `npx cap open android` → Android Studio → 에뮬레이터나 폰에서 실행.
- 앱 아이콘, 스플래시 화면을 넣는다. `@capacitor/assets`에 이미지 하나 주면 크기별로 자동 생성된다.
- 상태바 색, 뒤로가기 동작 같은 자잘한 조정도 이때 한다.

### 3단계. 푸시 알림 (1~2일)

- `@capacitor/push-notifications` 설치.
- iOS: Apple 개발자 콘솔에서 APNs 키 발급. Android: Firebase 프로젝트 만들고 FCM 설정.
- 앱에서 토큰을 받아 서버에 저장하는 API를 하나 추가한다. `app/api`에 들어가는 백엔드 작업이다.
- 새 트렌드가 뜰 때 발송하는 로직은 나중에 해도 된다. 심사용으로는 토큰 등록만 돼 있어도 된다.

### 4단계. 스토어 준비물 (하루)

양쪽 스토어 모두 필요하다.

- 스크린샷: iPhone 6.7인치, 6.5인치 각각. Android는 폰 기준.
- 앱 설명, 키워드, 카테고리.
- **개인정보처리방침 URL.** 웹에 페이지 하나 만들면 된다. 없으면 제출 자체가 안 된다.
- 지원 연락처 URL 또는 이메일.

### 5단계. iOS 제출 (심사 1~3일)

1. Xcode에서 Product → Archive → Distribute → App Store Connect 업로드.
2. App Store Connect 사이트에서 앱 정보 입력, 빌드 선택, 심사 제출.
3. 결과는 이메일로 온다. 거절되면 이유가 적혀 있고, 고쳐서 재제출한다.

흔한 거절 사유:
- 4.2 최소 기능 (웹뷰만 있고 네이티브 기능이 없음)
- 로그인이 있는데 테스트 계정을 안 줌
- 개인정보처리방침 누락

### 6단계. Android 제출 (심사 수 시간~수 일)

1. Android Studio에서 Build → Generate Signed Bundle → `.aab` 파일 생성.
   **서명 키는 잃어버리면 앱 업데이트를 영원히 못 한다. 반드시 백업.**
2. Play Console에서 앱 만들고 `.aab` 업로드, 스토어 정보 입력.
3. 처음엔 내부 테스트 트랙에 올려 확인한 뒤 프로덕션으로 승격한다.

신규 개발자 계정은 프로덕션 전에 **테스터 12명 이상, 14일 비공개 테스트**를 요구한다. Android에서 가장 시간을 잡아먹는 단계다.

### 7단계. 이후 운영

- 웹 화면 수정: 웹 배포만 하면 앱에 즉시 반영. 스토어 작업 없음.
- 아이콘, 플러그인, 네이티브 설정 변경: 앱을 다시 빌드해서 스토어 업데이트 제출.

### 소요 기간

순수 작업은 일주일 안쪽. 계정 승인, 심사 대기, Android 14일 테스트 때문에 달력상으로는 3~4주 잡는다.
