# 급상승 점수 검증 절차 도입 제안

> 작성일: 2026-09-10 · 목적: 팀 논의용 — `rising_score`/`급상승` 배지가 실제로 "진짜 트렌드"를 잡아내는지 확인할 절차를 붙이자는 제안.
>
> 최근 PR(`ea785cd 급상승 점수와 랭킹 배지 추가`)로 기능은 배포됐지만, 이 점수가 맞는지 확인하는 절차는 아직 없다.

## TL;DR

- **문제**: `rising_score`가 85점 이상이면 "급상승" 배지를 붙이는데, 이 점수가 실제 트렌드를 반영하는지 확인할 방법이 없다.
- **제안**: 검증 절차 2가지만 도입한다 — ① **속도 기반 노이즈 필터링**(내부 데이터만으로 가능), ② **외부 소스 교차검증**(네이버 검색광고 API, 이미 팀이 검토해둔 경로).
- **왜 이 둘만인가**: 같은 아이디어를 "네이버 자동완성 크롤링"으로도 검토했지만, 팀이 이미 `naver-api-research.md`에서 동일한 이유(정보통신망법 48조, 약관상 크롤링 금지)로 데이터랩 크롤링을 제외 처리한 것과 똑같은 리스크라 기각했다.
- **비용**: ①은 새 API·계정 없이 기존 스키마(`baseline_mentions`, `trend_snapshots`)만으로 시작 가능. ②는 이미 액션 아이템으로 잡혀 있던 검색광고 API 계정 발급이 전제조건.

---

## 1. 왜 지금 필요한가

현재 급상승 점수 산식(`docs/keyword-collection-and-ranking.md`)은 이렇다.

```text
급상승 점수 = (최근 1시간 언급량 ÷ (직전 5시간 평균 + 1)) × 50   [0~100 클램프]
```

이 산식에는 **구조적 약점**이 하나 있다: 분모(`baseline_mentions`)가 작을수록 절대 언급량이 적어도 점수가 쉽게 튄다.

| 직전 5시간 평균 | 최근 1시간 언급 | 급상승 점수 | 배지 노출 |
|---|---|---|---|
| 10회 (2회/시간) | 6회 | 100점 | O |
| 0회 | 2회 | 100점 | O |
| 0회 | 1회 | 50점 | X |

두 번째 줄처럼 **단 2건의 언급만으로도 만점이 나올 수 있다.** 글 하나, 댓글 하나만 우연히 겹쳐도 배지가 붙을 수 있다는 뜻이다. 지금은 이게 실제로 얼마나 자주 일어나는지, 그렇게 뜬 키워드가 진짜 트렌드였는지 확인할 절차가 없다. 배지는 사용자 신뢰에 직결되는 기능이라, 이 구멍을 먼저 메워야 한다.

---

## 2. 이게 왜 "검증"이 되는가

참고한 프레임워크([Binder 블로그](https://blog.teambinder.ai/trend-keyword-analysis))는 트렌드 판별을 4단계로 나눈다: 자동완성(초기 감지) → 연관검색어(확산 파악) → **VOC(교차 검증)** → **속도(노이즈 필터링)**. 이 중 실제로 "진짜냐 아니냐"를 판정하는 건 뒤의 두 단계뿐이고, 공통점은 둘 다 **"우리 산식 바깥에 있는 잣대로 다시 확인한다"**는 것이다.

| 원 프레임워크 | 검증 원리 | TrendDrop 적용 |
|---|---|---|
| VOC 교차검증 | 검색량과 무관한 **독립 신호**가 같이 움직이는지 확인 | risingScore 계산에 안 쓰인 외부 소스(네이버 검색량)와 상관관계 확인 |
| 속도 판단 | 절대량이 아니라 **baseline 대비 증가율**로 노이즈 제거 | 지금 산식에 없는 **최소 표본 크기 + 연속성 조건**을 얹어 저표본 노이즈 제거 |

"자동완성 리스트 변동"도 검증 후보로 검토했지만, 결국 검색 행동이라는 같은 모달리티 안에서 하나 더 보는 것일 뿐이고 — 그마저도 비공식 크롤링이 필요해 §4의 법적 리스크를 그대로 안는다. 그래서 제외했다.

## 3. 왜 우리 서비스 구조에 맞는가

| 근거 | 내용 |
|---|---|
| **이미 정해둔 역할분담과 일치** | `naver-api-research.md`가 "발견(디시/더쿠/인스티즈/유튜브/구글트렌드) → **검증**(검색광고·데이터랩) → 맥락(뉴스)"으로 역할을 나눠뒀다. 이번 제안은 그 "검증" 칸을 실제로 채우는 것뿐, 새 개념이 아니다. |
| **독립성 확보됨** | 현재 5개 원천(raw_signals) 중 검색 기반은 Google Trends뿐이고, 나머지는 커뮤니티·유튜브다. 네이버 검색량은 이 5개 중 어디와도 겹치지 않는 완전히 별도 플랫폼이라 순환검증이 안 된다. |
| **제품 정체성과 충돌 없음** | `domain-differentiators.md`는 "검색량이 아니라 SNS 반응이 차별점"이라고 못박아뒀다. 이번 제안은 네이버 검색량을 **점수에 반영하지 않고 검증에만** 쓰기 때문에, 순위 로직이 검색량 중심으로 오염될 위험이 없다. |
| **구현 비용이 낮음** | `trend_snapshots`에 `baseline_mentions`가 이미 있고, `trend.service.ts`에도 최근 run 이력(`scoreTrail`)을 쌓는 구조가 이미 있다. ①번은 새 인프라 없이 기존 데이터로 바로 시작 가능. |
| **이미 승인된 경로** | ②번에 쓸 검색광고 API 계정 발급은 `naver-api-research.md`의 "다음 액션 아이템"에 이미 올라가 있던 항목이다. 새로 설득할 일이 아니라 순서를 당기는 것에 가깝다. |

## 4. 어떻게 구현할 것인가

### ① 속도 기반 검증 (선행, 외부 의존 없음)

1. **최소 표본 조건 추가**: `baseline_mentions + 최근 1시간 언급`이 특정 값(예: 5건) 미만이면 점수가 높아도 배지 미노출. (위 표의 "2건으로 100점" 케이스를 원천 차단)
2. **연속성 조건 추가**: 단일 스냅샷에서만 85점을 넘긴 건 노이즈로 간주. 연속 2개 run에서 임계값을 유지할 때만 배지 확정.
3. **백테스트**: 과거 `trend_snapshots` 데이터에 위 조건을 적용해서, 배지가 붙었다가 다음 run에서 바로 꺼지는(=노이즈였던) 케이스가 얼마나 걸러지는지 비율로 측정.

### ② 외부 소스 교차검증 (후행, API 계정 필요)

1. 매일 1회, `rising_score` 상위 20~30개 키워드만 뽑아 네이버 검색광고 API 키워드도구로 최근 30일 검색량 조회.
2. 결과는 `trend_snapshots`와 별도 테이블(예: `external_validation`)에 저장 — **risingScore 산식에는 절대 재반영하지 않음** (순환검증 방지).
3. "우리 상위 키워드 중 외부 검색량도 같이 오른 비율"을 주기적으로 집계해 내부 대시보드/로그로 모니터링. 사용자에게는 노출하지 않음.

### 순서

**①을 먼저 붙인다.** 외부 API 없이 지금 스키마만으로 가능하고, ②의 "우리 신호가 얼마나 노이즈에 강한지"를 먼저 다져야 외부 비교가 의미 있어진다.

## 5. 결정 필요 사항 (팀 논의용)

- [ ] ①의 최소 표본 임계값(예: 5건)과 연속성 조건(예: 연속 2회)을 구체적으로 얼마로 잡을지
- [ ] ①의 백테스트 결과를 누가/언제 보고 배지 로직 수정 여부를 최종 결정할지
- [ ] ②를 위한 네이버 검색광고 API 계정 발급 담당자 및 일정
- [ ] `external_validation` 결과를 팀이 볼 대시보드 형태로 만들지, 아니면 로그/리포트로 충분한지
