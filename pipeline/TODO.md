## 1. 이슈 파편화 — 단어가 아니라 이슈를 뽑기

**문제.** 토크나이저가 제목을 단어로 쪼개면서 하나의 이슈가 흩어진다.

```
"현상금 1억 통영 살인사건용의자 CCTV사진.jpg"
   ↓ 토큰화
현상금 / 통영 / 살인사건용의자 / CCTV사진
```

`통영 살인사건`이라는 이슈가 조각으로 나뉘고, 각 조각은 점수가 낮아 후보 50개에 못 든다. 후보에 못 들면 LLM이 병합할 기회조차 없다. (`김윤희`+`아나운서`가 병합된 건 둘 다 gtrends라 40점씩 높았던 운 좋은 경우다.)

결과적으로 **엔티티는 뽑히지만 "무슨 일이 있었는지"는 사라진다.** 인스티즈 인기글 5개에서 실제로 건진 트렌드 키워드가 `모솔연애2`·`통영 살인사건` 둘뿐이었다.

### 대응 A — 입력 정제 (즉시, 무료)

수집기가 이미 분류 정보를 저장하고 있다.

- `instiz` → `meta.category` (일상 / 정보·기타 / 연예 / 드영배)
  - **`일상` 제외**하면 10건 중 5~6건이 입력 단계에서 빠진다
  - `주말 소개팅룩 봐줘`, `와 밖에 ㄹㅇ 찜통이네`, `꾸밈비용 너무 많이든디` 등
- `dcbest` → `meta.gallery` (`[XX갤]` 출처)
  - `싱갤`·`이갤`은 잡담성, `미갤`·`더갤`·`중갤`은 뉴스성

노이즈 입력은 줄지만 **파편화 자체는 해결되지 않는다.**

### 대응 B — 원문에서 이슈 통째로 추출 (근본)

한때 "월 $71이라 비싸다"고 접었던 A안. 조건이 바뀌었다.

| | 당시 | 지금 |
|---|---|---|
| 버킷당 원문 | 1,200행 / 12,500토큰 | **189행 / 9,500토큰** |
| 월 비용(Sonnet 5) | $71 | $48 |

네이트판과 인스티즈 `/pt`를 빼면서 물량이 줄었다. 여기에 결정적인 게 하나 더 있다 — **원문의 63%가 반복이다.**

```
youtube|comment  66% 재등장
dcbest|title     67%
theqoo|title     57%
youtube|title    70%
gtrends|title    25%
─────────────────────────
합계             63%  → 756행 중 고유 277건
```

같은 글이 여러 시간 랭킹에 머물기 때문이다. `text_hash`로 캐시하면 고유 원문만 LLM을 통과한다.

```
버킷당 189행 → 고유 약 70행만 처리
→ Sonnet 5  월 $18 안팎
→ Haiku 4.5 월 $6 안팎
```

지금 `keyword_verdicts`가 term에 대해 하는 일을, 원문(`text_hash`)에 대해 적용하는 구조다.

이러면 `현상금 1억 통영 살인사건용의자 CCTV사진.jpg` → **`통영 살인사건`** 하나로 나온다. 토크나이저도 불용어도 별도 필터도 필요 없어진다.

### 판단 시점

**며칠 데이터를 쌓은 뒤 결정한다.** 현재 4버킷뿐이라 근거가 얇다. 특히 반복률 63%는 4버킷 기준이라 실제로는 더 높을 가능성이 크다(디시 글이 6시간 머물면 6번 저장). 반복률이 확정돼야 B의 실제 비용이 나온다.

## 2. 카테고리 계수 결정

## 4. `raw_signals` 저장 공간 보존·정리 정책 (#96)

`raw_signals`는 수집 원문이자 재계산의 근거이므로, 보존 기간을 합의하지 않은 상태에서
자동 삭제하거나 임의의 기간을 적용하지 않는다. 저장 공간 한도에 가까워졌다는 이유만으로
즉시 물리 삭제하지 말고 아래 순서를 따른다.

1. **보존 기간 결정** — 데이터의 재계산 가치·운영 비용·삭제 복구 불가를 검토해 팀에서
   보존 기간을 먼저 확정한다. 확정 전에는 자동 정리 작업을 활성화하지 않는다.
2. **사전 점검** — `raw_signals`의 전체/기간별 행 수, 디스크 사용량, 가장 오래된
   `bucket_at`, 그리고 해당 기간을 참조하는 랭킹·수집 run을 read-only로 확인한다.
3. **dry-run** — 확정된 기준일에 따라 삭제 대상 행 수와 예상 공간 회수량만 계산하고,
   보존 기간 밖의 데이터가 재계산·감사에 필요한지 확인한다. dry-run 결과를 보관한다.
4. **승인 후 물리 삭제** — 명시적 승인 뒤 확정된 보존 기간을 넘긴 `raw_signals`만
   배치로 삭제한다. 삭제 쿼리는 대상 기간과 행 수를 먼저 출력하고 트랜잭션 단위로 실행한다.
5. **사후 검증** — 삭제 후 행 수·저장 공간·참조 무결성·수집/랭킹 파이프라인을 확인하고
   실행 시각과 결과를 기록한다.

현재는 보존 기간과 실행 승인이 없으므로 자동 삭제 스크립트·스케줄·DELETE 쿼리를
   추가하지 않는다. 보존 기간이 합의되면 별도 작업으로 dry-run과 승인된 정리 실행을
   구현한다.
